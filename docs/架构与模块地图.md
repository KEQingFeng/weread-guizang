# 归藏 · 架构与模块地图

这份文件回答「代码在哪、谁调谁、数据落在哪」。要改哪一层，先看这一份；
要遵守什么规矩，看同目录的 `开发规范.md`；装与跑看 `部署说明.md`；
接手这一轮的变化看 `交接说明.md`。

事实以 0.9.9 为准，行号会漂，函数名不会。

---

## 1. 全局形状

```
      浏览器界面  ui.html  （单文件，原生 JS/CSS，无构建）
            │  fetch /api/*  +  轮询 /api/state (2.6s) 与 /api/log
            ▼
   本地后端  ui_server.py  （只监听 127.0.0.1，标准库 ThreadingHTTPServer）
            │
            ├─ 同进程：书架/笔记/导出/阅读统计/云同步/小助手/订阅 → 直接 import 各模块
            ├─ 子进程：取书、登录、加书架、装组件、剪藏、视频转笔记 → py() + script(name)，cwd = 数据目录
            └─ HTTP：微信读书官方 Agent Gateway（用户自填 wrk- Key，只读）；
                     剪藏 / 订阅 / 视频侧只碰用户点名的源站（知乎/小红书/X、各 RSS、B 站/YouTube）
            │
            ▼
      本机数据   cache/（配置、封面、索引、日志、feed.json、tools/）
                ＋  书库/<书号>/（章节 md + 图 + 元数据，五种来源同一形状）

   两个入口包着同一套后端：
     · shell/  Swift 原生壳 → dist/归藏.app → 安装包/*.dmg（双击即用）
     · mcp/    Node stdio 适配器 → 把 HTTP 包成 32 个 MCP 工具，给 AI Agent 用（skills/ 是说明书）
```

要点：后端是**唯一真源**。界面、壳、MCP 三种入口共用同一份 `ui_server.py`，
所以「界面能干的，Agent 也能干」，反之加接口时三边同时受益。

0.9.9 之后取内容的通路从一条变成四条（取书 / 剪藏 / 订阅 / 视频），
它们唯一的共同点是**最后都落成一本形状相同的书**；中间过程各走各的，
合并在「落成书」这一步，而不是硬塞进同一个解析器。

## 3. 五条主链路

**取书（长任务，分钟到小时级）**

```
界面点「取书」→ POST /api/action {action:"export", book:<id 或链接>}
  → extract_book_id() 从链接里抠书号
  → start_task("export", [py(), script("export_precise.py"), book_id], book=book_id)
      · cwd = DATA_DIR，env GUIZANG_OUTPUT = OUT_DIR   （引擎里的 output/ 就是这么落对地方的）
  → 引擎逐行输出 → _reader() 线程：抓「📖 书名 — 作者」与「全书导出完成」，同时 log() 进内存环形日志
  → 界面每 2.6s 轮 /api/state 看 task.running，每 1.2s 重画进度；日志用 /api/log?tail=N
中止：POST {action:"stop"} → stop_task() → pc.send_stop()（POSIX SIGTERM / Windows CTRL_BREAK）
      引擎收到后把手上那一章攒完再落盘；60s 内没退才 pc.hard_kill()
清掉重取：{action:"export.fresh"} → 先确认没有任务在跑，再 reset_book_output()，然后起新任务
      （顺序反了就会留下「书被清空 + 任务没起来」的最坏局面）
```

`done` 只在看到「全书导出完成」那行才置位，中止永远显示为「取到一半」——
0.9.8 那道谎就是这么修的。前端另按「已取章数 / 目录总章数」复核一次，两边都说齐了才算齐。

**页内读（不进浏览器也能读）**

```
GET /api/read?book=<id>            → 左栏目录（book_outline）
GET /api/read?book=<id>&ch=<文件>  → 该章正文（不给 ch 就是目录）
GET /api/md /api/img               → 单章源文与图片直读
右栏「边读边记」→ /api/mynotes（这本书的 notes.json）
                → /api/mynotes/export、/api/note_tpl、思维导图 /api/mynotes/map
正文渲染用 vendor/ 里的 markdown-it，不连 CDN。
```

**剪藏（含知乎 / 小红书 / X）**

```
POST /api/clip {urls:[…]}（一次最多 20 条）
  → 按 host 分流：知乎 / 小红书 / X 走 web_parse，其余（尤其公众号）走 clip_article
  → 抓到正文 → 一本 clip_<id> 书入库 → 书架里当普通书读、导 EPUB/PDF
拿不到就如实报错：三家未登录时常只回「安全验证」页，这里认出来就说不成，不绕过登录态。
```

**订阅（RSS）**

```
GET  /api/feed?mode=list|entries|entry      → 订阅列表 / 条目 / 单条（只读，自己不抛）
POST /api/feed {act:"discover"|"add"|"remove"|"mark"|"refresh"|"read"|"shelf"}
  → add：给个网址即可，只给站点首页也行——discover 从 <link alternate> 挑最好的源
  → refresh：按源抓增量（ETag / Last-Modified），逐源隔离错误，一个坏了不拖垮其余
  → shelf：feed.to_shelf() → 一本 feed_<id> 书入库；全文够长直接用，只有摘要才回源抓正文；同一 entry 不重复入库
存储：cache/feed.json；不发请求的活（列、读、标）都在进程内，刷新也只在被调用时发生。
```

**视频转笔记**

```
GET  /api/video?mode=status|plan            → 可用性（yt-dlp / ffmpeg / ASR 引擎 / LLM）/ 认链接列分 P
POST /api/video {act:"start"|"ffmpeg"|"stop"}
  → start：start_task("video", [py(), script("video_note.py"), "--task", url],
                       env_extra={"GUIZANG_VIDEO_OPTS": {asr, language}})
      · 长任务，立即返回；进度靠 /api/state 的 video 段与 /api/log 轮询
  → 流水线（都在子进程内）：plan → download（yt-dlp 取音频）→ asr → summary → note → mindmap → save
  → 一本 video_<id> 书入库；只会转链接里点的那一 P；音频只落临时目录，转完即删
  → LLM 三件套（url/key/model）由 ui_server 从 config 取好，经 opts 传进去；视频模块不 import ui_server
  → AI 缺席不算失败：转写照存、书照进，结果里带 ai_error 说明原因
  → ffmpeg：POST {act:"ffmpeg"} → start_task("ffmpeg", […, "--ensure"])
```

## 4. 数据落在哪

| 路径 | 装成 app | 源码直接跑 |
|---|---|---|
| 数据根 `DATA_DIR` | `~/Library/Application Support/归藏/` | 项目目录本身 |
| 书库 `OUT_DIR` | `~/Documents/归藏/` | `DATA_DIR/output/` |
| 虚拟环境 | `DATA_DIR/.venv/`（`platform_compat.venv_dir`） | 项目 `.venv/` |

`DATA_DIR/cache/` 里的东西：

| 文件 | 内容 |
|---|---|
| `config.json` | 微信读书 API Key、小助手地址/Key/模型、flomo webhook、导出目录偏好 |
| `login_state.json` | 登录态快照（界面与 MCP 都读它） |
| `library.json` | 本地藏书表：文件夹、每本的状态标签、排序 |
| `covers/` | 封面缓存 |
| `notes_index.json` | 全书划线索引（`build_notes_index` 造，可重建） |
| `readstat.json` | 本机阅读时长，按天累计（微信读书那边另有来源，界面上合并显示） |
| `wallpaper.bin` | 自定义壁纸 |
| `note_templates.json` | 用户自建笔记模板 |
| `feed.json` | 订阅源与条目（0.9.9 加）；只读轮询会缓存一份按 (mtime, size) 的摘要，几千条也不卡 |
| `tools/` | 按需下载的静态 ffmpeg/ffprobe（0.9.9 加），不碰系统目录 |
| `downloads/` | EPUB/PDF/ZIP 成品落地处 |

一本书的目录（`书库/<书号>/`）——**取回、导入、剪藏、订阅、视频五种来源都是这一套形状**，
所以阅读器、导出、定位文件都不用区分来源：

```
meta.json        title / author / done / source / chars / updated_at
                 非微信读书来源另有 format（local/clip/feed/video）与各自附加字段：
                 clip → url；feed → feed_id / feed_title / date；video → url / asr_engine / duration
_catalog.json    [{"chapterTitle": "第N章"}…]，长度＝总章数（进度分母）
chapters/0001.md 逐章正文（图文按阅读顺序交错）
raw/NNNN.json    每章一份：图片 URL 与 text_len（书架上的字数按它累加）
images/          正文图片
_progress.json   引擎实时进度（翻到第几页），一章内部进度条靠它
notes.json       归藏里的划线与批注 {schema, marks[], entries[]}；读坏先备份 .bad-<ts>
notes.md         笔记的 Markdown 导出（视频来源落书时一并生成）
mindmap.svg      按大纲画的思维导图
```

视频来源那本还会在落盘时把 `notes.md` / `mindmap.svg` 一并与书同目录写入；
四种非微信来源的 `format` 字段就是给书架分组用的，别拿 `source` 之外的东西判来源。

`reset_book_output()` 清残稿时只删 `chapters/ raw/ images/ _catalog.json _progress.json`
和书库根上的合并稿，`meta.json` 与 `notes.json` 保留 —— 取书失败不该让人连带丢笔记。

## 5. 两套 id，别混

| 名字 | 形状 | 用在哪 |
|---|---|---|
| 阅读器 id | 18–24 位字母数字混合，来自 `deepLink` 里的 `v=` | **本地目录名**、`/api/*` 的 `book=` |
| 书架 bookId | 书城短号，`/shelf/sync` 每条里的 `bookId` | 官方只读接口（`/book/info`、`/book/getprogress`…）、`shelf_add` |

从详情页、划线搜索、书城搜索进来的常常是后者。传错命名空间不会报错，只会**装作没有**：
`book_id_pairs()` 的注释写着「明明有划线却说没有」，`/api/detail` 会把已抓取的书
显示成「尚未抓取」——这类静默错乱比抛异常难查得多。
处理办法是后端自己换算：`store_to_reader_map()` :1388 拉一次 `/shelf/sync`，
用 `deepLink` 里的 `v=` 建「bookId → 阅读器 id」映射，缓存 10 分钟，失败用旧值；
`book_id_pairs()` :637 则两个方向都试。前端传来的字符串一律先过 `extract_book_id()`。

本地来源带前缀区分，一本书属于哪条通路看前缀就够：
`imp_<名>` ＝ 自己导入，`clip_<名>` ＝ 剪藏（含知乎/小红书/X），
`feed_<名>` ＝ 订阅条目，`video_<名>` ＝ 视频转笔记。
这四类都不带微信读书的命名空间，也就不会去查官方接口。
`safe_book_dir()` 负责挡掉路径穿越，`book_id` 形状不对就不碰磁盘。

## 6. 接口面（全在同一文件，全 JSON）

- `GET` 状态与只读：`/api/state`（界面唯一的轮询源）、`/api/log`、`/api/readstat`、
  `/api/detail`、`/api/cover`、`/api/wallpaper`、`/api/mcp`（一键接入提示词）、
  `/api/notes_index`、`/api/notes_search`、`/api/notes_random`、`/api/notes_of`、
  `/api/read`、`/api/md`、`/api/img`、`/api/feed`（订阅列表/条目）、
  `/api/video`（可用性/认链接）
- `GET` 产物下载：`/api/zip`、`/api/zip-multi`、`/api/apkg`、`/api/epub`、`/api/pdf`、
  `/api/mynotes`、`/api/mynotes/map`、`/api/note_tpl`
- `POST` 动作：`/api/action`（一个入口，body 里 `action` 分发：`export`、`export.fresh`、
  `stop`、`login`、`install`、`log.clear`、`export_dir`、`agent.save`、`agent.test`…）、
  `/api/weread`（官方只读接口透传）、`/api/config`、`/api/book_state`、`/api/import`、
  `/api/delete_many`、`/api/clip`、`/api/mynotes`、`/api/mynotes/export`、`/api/note_tpl`、
  `/api/wallpaper`、`/api/flomo`、`/api/sync/*`、`/api/agent/chat`（这条走 SSE 流）、
  `/api/agent/quick`、`/api/readstat/tick`、`/api/readstat/clear`、
  `/api/feed`（`act` = discover/add/remove/mark/refresh/read/shelf）、
  `/api/video`（`act` = start/ffmpeg/stop）

订阅与视频这两条不走 `/api/action`，各自是独立路由（`feed_view`/`feed_do`、
`video_view`/`video_do`）：它们的分支多、又都要自己兜住异常，
塞进 `_dispatch` 会让那一层的 try 兜底看不清边界。

新增动作优先加进 `_dispatch()` 而不是开新路由：那一层外面有 try 兜底，
异常会回一句人话；自己开路由就得自己处理「抛异常把连接掐断」这个坑。
`_action` 兜底由 `tests/test_server_fallback.py` 守着。

## 7. 前端（ui.html 一个文件，约 9.4 千行，没有构建步骤）

- 结构：视图面板 `.vpane` 常驻 DOM，切视图只改 class 与属性，**不整块重建**
  （重建会「点一下闪一下」，第 29–30 项修的根因）。`[hidden]` 与 class 两套都要留意。
- 冷启动的屏：`render*View` 先铺与真实结构同形的骨架（`skelLines` / `skelRows` /
  `skelCards` / `skelStats`），数据到了才换真内容；`pane.dataset.sig` 挡住同数据重铺。
  悬停预取三件套 `prefetch` / `preAwait` / `hoverAhead`（`PRE_TTL` 10s、`PRE_DWELL` 90ms）。
- 玻璃层是数得清的：开合浮层（`.rdpop` / `.ntlay` / `.veil` / `.pop` …）用 `visibility`
  门控，收起来就不参与合成；纸面（`--paper` 一族）是实心色，故意不吃磨砂滑杆。
- 阅读器状态 `RD`：`{book, chapters, at, ol, olAt, olReady, resumeCh, resumeY, back}`。
  读到「哪一章 + 页内第几行」落在本机 `localStorage` 的 `guizang-readpos-<book>`，
  停手 800ms 才写，开书回到那一行、那一笔偏移只用一次；本章大纲（`rdOutline` /
  `rdOlMeasure` / `rdOlActive`）只在打开浮窗那一刻量一次各节偏移，之后滚动只比数字。
  笔记状态另在 `NT`，写作层在 `NTED`。
- 数据来源：`drawState()` 每 2.6s 拉 `/api/state`；进度条另有 1.2s 的本地补间；
  日志按 `tail` 拉增量。没有虚拟 DOM、没有框架、没有 CDN 依赖
  —— 断网也能跑，`vendor/markdown-it.min.js` 是随包的。
- 书架两种排法：羊皮卷瀑布流 / 果冻叠卡，模式选择要跨刷新活下来。
- 0.9.9 新增两屏：**订阅**（源列表 + 条目列表 + 单条入书架/标已读/退订/刷新）与
  **视频转笔记**（贴链接 → 认分 P → 选引擎与语言 → 起任务 → 结果落书架）。
  视频这屏有个可复用的坑：卡片空态靠「列表指纹」判断有没有变化，
  空列表与初值都是空串就会永远认为没变——指纹要带上条数（见 `开发规范.md` 的教训）。
- 无头实测的四条硬事实（写断言前必须知道）：
  1. `flush()` ＝ 两次 `requestAnimationFrame` ＋ `document.getAnimations().forEach(a => a.finish())`；
  2. 容器查询量的是**内容盒**（`clientWidth − padding`），且不能给自己的容器改样式；
  3. 界面零 emoji 的判据是 `innerText` 与源码两处（源码唯一豁免是 `STRIP = ` 那行清洗正则）；
  4. 性能对照只认**同一次运行内的 A/B**：把 `git show HEAD:ui.html` 用 `page.route`
     顶掉首页，与工作树在同一台机器上各跑一遍比 CDP `Performance.getMetrics` 的增量。
     跨浏览器实例的绝对值会飘（无头 rAF 计时尤其不可信），脚本顶层的 `const`
     也不挂在 `window` 上，探针要用裸名字 + `typeof` 兜底。

## 8. 外围三块

| 目录 | 干什么 | 契约 |
|---|---|---|
| `shell/` | `main.swift` 原生壳（起服务、进度回推、首启页 `onboarding.html`）、`build_macos.sh` 出 `dist/归藏.app`、`make_dmg.sh` 出 `安装包/*.dmg` | 版本号从 `ui_server.py` 读；`APP_FILES`/`APP_DIRS` 是进包清单的唯一出处；壳通过 `GUIZANG_DATA`/`GUIZANG_BOOKS`/`GUIZANG_PYTHON` 指路，并设 `PYTHONDONTWRITEBYTECODE=1` 保持包体只读 |
| `mcp/guizang-mcp.mjs` | 零依赖 stdio 适配器，把 HTTP 包成 32 个 MCP 工具（书架 6 / 取书 4 / 书与笔记 7 / 剪藏 1 / 订阅 8 / 视频 3 / 导出 3），服务没起就自己拉起来 | 长任务不阻塞：`book_fetch` 与 `video_to_shelf` 立即返回，进度靠 `app_status`/`task_log` 轮询；**`feed_*` 只动本地状态，不写微信读书书架**，唯一的真实书架写入是 `shelf_add`；动手前先用 `video_capability` 问一句 |
| `skills/` | `guizang`（用自然语言操作归藏）与 `book-speedrun`（把一本书讲透） | 只写「先查状态再动手、写操作只做用户点名的那个」这类判断，不重复工具参数 |

## 10. 加一个功能的最短路径

1. 想清它属于哪个模块。新的独立能力就照 `clip_article.py` 的样子单开一个文件，
   开头写清「为什么单独一个文件」；否则并进已有模块的对应函数群。
2. 后端：写函数 → 在 `_dispatch()` 或 `do_GET`/`do_POST` 挂上 → 返回 `{ok, msg, …}`，
   `msg` 给人看，失败也要是人话。
3. 前端：`ui.html` 里加控件与调用；只改属性不重建视图；文案对齐现有措辞；零 emoji。
4. **进包清单**：新文件补进 `shell/build_macos.sh` 的 `APP_FILES` / `APP_DIRS`。
   漏了 = 源码跑一切正常、装成 app 一点就哑，而这正是本仓库唯一没法在本机
   用户视角复现的路径。源码包会从同一份清单派生，不用两处改。
5. 测试：能在进程内测的写 `tests/test_*.py`；要点才的写 `tests/check_*.py`
   （从 `selftest` 取路径、夹具 `atexit` 自清），并加进 `tests/run_all.sh`。
6. `bash tests/run_all.sh` 全绿 → README×3 的「更新记录」补一句 →
   `docs/交接说明.md` 补上这一轮的新模块与新边界 →
   按 `开发规范.md` §8 发版。

**如果新功能是「又一条取内容的通路」**：照 `feed.py` / `video_note.py` 的样子单开文件，
让它最终落成一本形状相同的书（`meta.json` + `chapters/` + `raw/`），
在 `_dispatch` 之外单开一个 `*_view` / `*_do` 路由，
并把来源前缀注册进 `safe_book_dir()` 与书架的来源分组。别去改通用解析器。

## 11. 已知的边界（别当成已完成）

- Windows 只做到「脚本与平台分支齐了、单测假跑过」，**没有出 .exe，也没有真机验证**。
- `.app` 未做签名与公证：首次打开要右键「打开」，`dmg` 里那份说明是给这一步的。
- 取书依赖微信读书网页阅读器的渲染方式（正文画在 Canvas，所以 Hook `fillText`）。
  对方改版就可能整片失效，这类失效在界面上表现为「抓不到正文」而不是报错。
- EPUB 是标准库手搓的，`mimetype` 必须是 zip 首个条目且 STORED —— 动它之前先读
  `book_export.py` 开头那段；未在各类阅读器做过全面兼容矩阵。
- 划线/进度等只读数据全部依赖用户自填的 `wrk-` Key 与本机登录态；
  `wr_skey` 过期会表现为「加书架失败」，处理是 `shelf_add.renew_session()`。
- 阅读到的**行级位置**只存在本机 `localStorage`（`guizang-readpos-<book>`），
  换浏览器、换机器、清站点数据都会掉，退回「记住上次读到第几章」那一层。
  它不参与云同步 —— 云同步走的是账号侧的阅读时长与笔记文件。
- 本章大纲只到 `h1~h3`、每章封顶 60 条：再深的层级属于正文结构问题，不是导航问题。
- 全文搜索没有做（`/api/notes_search` 搜的是划线与想法，不是书本正文）。
- 知乎 / 小红书 / X 的解析依赖对方「现在」怎么发页面，随时可能失效。未登录时
  知乎与小红书多数情况只回验证页——这是平台限制，**不做登录态绕过**也就没有
  cookie 上传问题；失效时如实报错，别把它改成静默失败。
- RSS 只做「订阅 → 读 → 入书架」这条最小闭环：不做已读/未读与账号侧双向同步，
  不做后台定时轮询（要新内容得点刷新）。`cache/feed.json` 是唯一存储，不参与云同步。
- 视频这条线第一版只支持 B 站与 YouTube；转写用通用 Whisper，专有名词/多人对话/
  强口音不保证。本地转写首次要下模型（large-v3-turbo 约 1.5 GB），下过常驻本机。
- `yt-dlp` 属于「随平台改版天天要更新」的工具：视频取不到时先
  `.venv/bin/pip install -U yt-dlp` 再试。这条不是 bug，是这类工具的性质。
- ASR 引擎（mlx-whisper / faster-whisper）**不在默认依赖里**：体积大且分平台
  （mlx 只在 Apple 芯片上跑），留在可选、按需装。`bootstrap.py` 的依赖门禁
  只列 `playwright, genanki, pypdf, feedparser, yt_dlp` 五项，别往里加 ASR。
- 视频任务的真跑链路（真下载 + 真转写）只在 `GUIZANG_VIDEO_LIVE=1` 时跑，
  默认门禁是离线夹具；也就是说**喉咙那一段没有被日常门禁覆盖**，改它要另跑一次真链路。
